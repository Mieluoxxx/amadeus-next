# 本质复杂度与偶然复杂度

本文按 Brooks 的划分审视 Amadeus-Next：**本质复杂度**来自产品要解决的问题本身，去不掉，只能实现得更好；**偶然复杂度**来自我们选择的实现方式，可以通过改变选择来消除。

判断依据是模块级的结构与注释，不是逐行审阅；比例与行数是估算，用来排优先级，不作为精确度量。

## 规模

`src` 约 2.4 万行，分布如下：

| 区域 | 行数 | 说明 |
|---|---|---|
| `src/main/durable` | 11.6k | worker：会话、事件桥、委托、记忆、远程 |
| ├ `memory/` | 3.9k | 长期记忆 |
| ├ `handoff/` | 3.6k | 子代理委托 |
| └ `remote/` | 1.0k | SSH 远程执行 |
| `src/main` 其余 | 3.7k | 主进程，其中 `appRuntime.ts` 1.4k |
| `src/renderer` | 6.8k | 设置页、聊天、工作面板 |
| `src/scene` + `resources/scene` | 2.6k | 场景、口型、表情 |
| `src/shared` | 1.0k | 呈现、对齐、导演协议 |

## 本质复杂度

| 需求 | 落在哪里 | 为什么省不掉 |
|---|---|---|
| 实时语音对话 | ASR → 流式 LLM → 流式 TTS → 播放 | 延迟是核心体验，每一段都必须流式 |
| 谁在说话 | `floor.ts` | 打断、回声、汇报何时插话都是真实问题；这部分已经很精炼 |
| 中文输入、日语语音、中文字幕 | 配音导演 + `AlignmentTimeline` | 两种语言按音频时间轴对齐，是需求本身 |
| 角色表现 | E-mote 烘焙、口型、表情 | 资源格式（PSB）决定了需要烘焙 |
| 能做事的伴侣 | 委托子代理、工具审批、路径守卫 | 只要 agent 能动文件、跑命令，安全边界与主人确认就省不掉 |
| 后台任务跨重启存活 | durable 存储、汇报信箱 | 长任务在重启后还能汇报，天然需要持久化与幂等 |
| 记得主人 | 长期记忆的存储与召回 | 人设连续性需要它；隐私与防误记是真实约束 |

## 偶然复杂度

按"代码量 × 心智负担"排序。

### 1. 让模型输出协议文本

双语标签解析器、`TagScrubber`、`toolText` 纠正钩子，都源于"用自由文本承载结构化协议"。主模型在一条流里同时遵守人设、双语成对、表情、语气、可念性五套规则，格式错误频繁，还会把工具调用写成正文。

**状态**：2026-10-16 起由配音导演取代，主模型只写中文，日语与表情由导演以 JSON 返回（见 `architecture.md` §4.4）。

**残余**：记忆与子代理结果仍以 `<amadeus_*>` 标签注入上下文，模型会复述，需要清洗器剔除（`durable/scrub.ts`）。根源相同，规模较小。

### 2. 两个进程各自维护回合状态

主进程的 `ActiveTurn` 与 worker 的 run 是两个状态机，靠一套协议同步：`turn:` / `report:` 前缀的 requestId、epoch、abort 旁路、命令分道、checkpoint/resume，以及一个 120 秒看门狗——它存在的理由是"终止事件可能丢"（`appRuntime.ts` 的 `TURN_WATCHDOG_MS`）。

把 Pi 与 UI 隔离到两个进程是合理的；偶然的是两边都持有状态。理想形态是一边持有、另一边只做投影。

### 3. 适配 pi-durable 事件模型

`eventBridge.ts` 的大部分逻辑在消化库的事件语义：第一段文本不一定来自 delta；积压超过 100 批改发快照，需要按快照做差；同一批事件里 `run_end` 排在 submission 之前、`run_start` 排在其后。这些是选择这个库的代价，与需求无关。

### 4. 每会话一库带来的派生缓存

真实数据分散在每个会话的 `durable.sqlite` 里，于是库外需要 `sessions/index.json`（`SessionIndex`，附校验与重建）和 `work.json`（`WorkLedger`），worker 启动时还要"不阻塞 ready 地重建索引"。

### 5. 配置经环境变量传递，变更需重启 worker

代理、委托模型、翻译模型、skills / MCP 模式都经 `piEnv()` 变成环境变量，改一次就重启 worker。连带出：重载排队、等播放结束、checkpoint 交接，以及 `index.ts` 里"继承来的同名环境变量不能悄悄生效"的防御。改成热更新命令，这条链路可以整段删除。

### 6. `AppRuntime` 职责过多

一个 1.4k 行的类同时承担设置校验、回合生命周期、会话缓存与乐观标题、角色资源导入、场景握手、重载编排。这些职责彼此独立，只是住在同一个类里。

### 7. 上一代项目的残留

- 设置页仍认 `qwen3_asr`、`sense_voice`、`mimo`、`tts_embedded_v3`、`wake_asr` 等后端（`SettingsPage.tsx`），主进程从不下发它们，i18n 里也留着对应文案。
- 源码中"旧"出现约 60 处、"v1"12 处、"遗留"12 处，另有 `AMADEUS_NEXT_DURABLE_SESSIONS` 之类的旧名兼容。

### 8. 记忆写入闸门（介于两者之间）

记忆模块比委托模块还大。`memory/gate.ts` 是一套手写规则引擎：jaccard 相似度、引用覆盖率阈值、中日英三套"相对时间"词表、每分钟限速。防误记是本质需求；用大量启发式去约束 LLM 提取，是偶然的。应先统计各条规则的实际命中，再决定去留。

## 估算

- 本质部分约 50%：语音链路、对齐、话筒仲裁、委托与安全、记忆核心存储。
- 偶然部分约 50%：上述 1–7，加上记忆规则中可精简的部分。

## 建议路线

按"收益 ÷ 风险"排序：

| 顺序 | 动作 | 收益 | 风险 |
|---|---|---|---|
| 1 | 删除第 7 节的死代码与残留后端（2026-10-16 已完成） | 立刻减少困惑 | 极低 |
| 2 | 配置改为热更新命令，不再重启 worker（2026-10-16 已完成，见 `architecture.md`「设置的热更新」） | 删除整条重载链路 | 低 |
| 3 | 拆分 `AppRuntime` 为回合控制、设置、会话 | 降低心智负担 | 中，有测试兜底 |
| 4 | 记忆与子代理结果改走结构化通道，不再用标签注入正文 | 清洗器退场 | 中 |
| 5 | 回合状态只由 worker 持有 | 看门狗与大部分同步协议退场 | 高，属架构调整 |
| 6 | 统计记忆闸门的规则命中，再做删减 | 缩小记忆模块 | 需要先有数据 |
